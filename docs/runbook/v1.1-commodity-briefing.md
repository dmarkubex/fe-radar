## 1. 节假日表年度维护 SOP

**触发时机**：每年国务院公布下一年度法定节假日安排后（通常 11 月底 / 12 月初），由 admin 执行本 SOP。

**影响**：未录入的节假日将在当日 15:30 / 16:00 / 16:05 正常触发三个 BullMQ job；若当日无行情数据（市场休市），quotes-fetch 会因字段覆盖率 < 5 触发 briefing-gen abort（`gen_status='failed'` + 红色告警）。及时录入可避免误报告警。

### 步骤

1. **登录 admin 后台** `/admin/briefing/targets`（当前 v1.1 暂无专属节假日管理 UI，走 SQL 直连或 admin API）。

2. **确认节假日列表**：从国务院官网或人社部公告中整理下一年度全部法定节假日日期（含调班补班后的实际休假日，仅记休假日，调班工作日不录入）。2026 年示例（11 天）：

   ```
   2026-01-01（元旦）
   2026-02-17..2026-02-23（春节 7 天）
   2026-04-04..2026-04-06（清明 3 天）
   2026-05-01..2026-05-05（劳动节 5 天）
   2026-06-19（端午）
   2026-10-01..2026-10-07（国庆 7 天）
   ```

3. **插入 `briefing_holidays` 表**（幂等，重复执行安全）：

   ```sql
   INSERT INTO briefing_holidays (holiday_date, name) VALUES
     ('2027-01-01', '元旦'),
     ('2027-01-28', '春节'),
     ('2027-01-29', '春节'),
     ('2027-01-30', '春节'),
     ('2027-01-31', '春节'),
     ('2027-02-01', '春节'),
     ('2027-02-02', '春节'),
     ('2027-02-03', '春节')
     -- ... 补全全年
   ON CONFLICT (holiday_date) DO NOTHING;
   ```

4. **验收**：

   ```sql
   SELECT COUNT(*) FROM briefing_holidays WHERE holiday_date >= '2027-01-01' AND holiday_date < '2028-01-01';
   -- 预期：≥ 11（实际视公告而定）
   ```

5. **记录**：在 Linear 对应年度 issue 留评论，记录录入日期和操作人。

> **注意**：`briefing_holidays` 是配置类表，永久保留（不在 90 天 cleanup 范围内）。v1.2 计划评估接入第三方节假日 API 自动同步。

## 2. 钉钉 Webhook 凭据轮换流程

**触发时机**：信息中心定期轮换（建议每 90 天）或疑似凭据泄漏时立即执行。

**安全要求**：webhook URL + sign_secret 不得出现在 git / 日志 / 前端 HTML 中；轮换期间会有短暂推送中断（预计 < 5 分钟）。

### 步骤

1. **信息中心**：在钉钉开放平台为目标群的自定义机器人重新生成 sign_secret（或删除重建机器人获取新 webhook URL）。

2. **admin 登录** `/admin/briefing/targets`，找到对应推送目标行，点击"编辑"。

3. **更新字段**：
   - 若 webhook URL 变更：粘贴新 URL 到"Webhook URL"输入框
   - 必须更新：粘贴新 sign_secret 到"加签 Secret"输入框（`type=password`，显示为掩码）
   - 点击"保存"

4. **测试推送验证**：点击"测试推送"按钮，观察 toast 提示。成功则新凭据生效。

5. **Grafana 确认**：观察 briefing-push 成功率面板，确认下一个工作日推送正常。

6. **旧凭据**：通知信息中心可在钉钉开放平台作废旧凭据（若是重新生成 secret，旧 secret 已自动失效；若是重建机器人，确认旧 webhook URL 已无效）。

> **安全审计**：admin 对 `briefing_targets` 的每次 PUT/DELETE 操作均写入 v1.0 `audit_logs` 表，可事后核查操作人与时间戳。

## 3. 模板 docx 改版流程

**触发时机**：简报模板版式 / 占位符 / 页脚声明需要调整时。

**约束**：模板纳入 git（`design/templates/briefing.docx`），不允许在运行时通过 UI 上传替换；改版必须走 PR + lint 校验。

### 步骤

1. **备份当前模板**：

   ```bash
   cp design/templates/briefing.docx \
      design/templates/briefing.v$(date +%Y%m%d).docx.bak
   ```

2. **本地编辑 docx**：用 Microsoft Word / LibreOffice 打开 `design/templates/briefing.docx`，修改版式或占位符。
   - 占位符命名规范：`{{<commodity>.<group>.<metric>}}`，例如 `{{cu.price.shfe_main}}`
   - 所有新增 `{{key}}` 必须同步在 `briefing_template_fields` 表新增对应行（通过新 migration，不能直接改 0009）
   - 页脚必须保留声明："仅供远东控股内部决策参考，禁止外传 / 不构成投资或采购建议"

3. **bump template_version**：确定新版本号（整数递增），在 `design/templates/briefing.docx` 内 `{{template_version}}` 占位符对应位置加注版本号说明（或通过 migration 更新 `briefing_template_fields` 默认值）。

4. **运行 lint 校验**（需 worker 开发环境）：

   ```bash
   # 在 worker 容器或本地 dev 环境执行
   pnpm --filter @fe-radar/worker run briefing:lint
   # 等价于：ts-node apps/worker/src/lib/briefing-render.ts --lint-only
   # 预期输出：✅ All {{placeholders}} resolved in briefing_template_fields
   ```

   若出现 `UNRESOLVED_PLACEHOLDER: {{key}}` 错误，需先通过新 migration 在 `briefing_template_fields` 补充该 key。

5. **新建 migration**（如有新占位符）：

   ```sql
   -- packages/db/migrations/0010_briefing_template_v2.sql
   INSERT INTO briefing_template_fields (placeholder_key, label, source_metric, fallback_text)
   VALUES ('cu.new_field', '新字段标签', 'cu_new_metric', '—')
   ON CONFLICT (placeholder_key) DO NOTHING;
   ```

6. **提交 PR**，包含：
   - `design/templates/briefing.docx`（二进制更新）
   - 新 migration 文件（如有）
   - `template_version` bump 记录

7. **部署后模板路径确认**：新版模板由 `deploy/Dockerfile.worker` COPY 到 worker 镜像内 `/app/design/templates/briefing.docx`，并通过 `stack.yml` 的 `BRIEFING_TEMPLATE_PATH=/app/design/templates/briefing.docx` 注入；无需手动上传模板到 MinIO（MinIO 只存渲染后的 docx 产物）。

8. **MinIO bucket lifecycle 确认**：`fe-radar-briefings` bucket 的 lifecycle policy 应设置对象 90 天后过期（对应 FR-110 / NFR-103）：
   ```json
   {
     "Rules": [
       {
         "ID": "briefing-docx-retention",
         "Status": "Enabled",
         "Expiration": { "Days": 90 }
       }
     ]
   }
   ```
   推荐用 `deploy/scripts/minio-provision.sh` 初始化并验收：
   ```bash
   docker run --rm --network fe-radar_internal \
     --entrypoint /scripts/minio-provision.sh \
     -e MINIO_ENDPOINT='http://minio:9000' \
     -e MINIO_ACCESS_KEY='<minio-user>' \
     -e MINIO_SECRET_KEY='<minio-password>' \
     harborssl.fegroup.cn/custom-project/fe-radar/backup:latest
   ```
   使用 `mc ilm ls fe-radar/fe-radar-briefings` 或脚本输出确认规则已生效。

## 4. 失败重推 SOP

### 4.1 简报生成失败（gen_status = 'failed'）

**现象**：Grafana `briefing-gen 成功率` 红色告警；`/briefing` 列表当日行显示"生成失败"。

**排查步骤**：

1. **查 Grafana Loki 日志**（filter `job=briefing-gen, level=error`）确认失败原因：
   - `QUOTES_FETCH_QUEUE_STALE`：quotes-fetch 队列积压 → 等待队列清空后手动重推（步骤 2）
   - `COVERAGE_INSUFFICIENT`：字段覆盖率不足（< 5 字段）→ 检查 quotes-fetch 各 adapter 状态（步骤 3）
   - `KIMI_GENERATION_FAILED`：Kimi K2.6 调用失败 → 检查 LLM 服务状态后重推
   - `BRIEFING_RENDER_FAILED`：docx 渲染失败 → 检查模板 lint（步骤 4）

2. **手动重新生成**（editor+ 权限）：

   ```bash
   curl -X POST https://fe-radar.internal/api/briefing/<id>/regenerate \
     -H "Cookie: <auth-cookie>"
   # 或在 /briefing/[id] 详情页点击"重新生成"按钮
   ```

3. **检查 quotes-fetch adapter 状态**：

   ```sql
   -- 查看当日字段覆盖情况
   SELECT metric_key, value, source_id, fetched_at
   FROM commodity_quotes
   WHERE observed_at::date = CURRENT_DATE
   ORDER BY metric_key;

   -- 查看各 source 失败计数
   SELECT id, name, fail_count, enabled
   FROM sources
   WHERE fetcher_type = 'quotes'
   ORDER BY fail_count DESC;
   ```

   如某 source `fail_count` 过高，到 `/admin/sources` 暂时禁用该 source 后重推。

4. **模板 lint 失败**：
   ```sql
   -- 检查是否有 active=false 的 placeholder
   SELECT placeholder_key, label, is_active FROM briefing_template_fields WHERE is_active = false;
   ```
   按第 3 节流程修复后重推。

### 4.2 钉钉推送失败（push_status = 'failed'）

**现象**：Grafana `briefing-push 成功率` 红色告警；`/briefing/[id]` 推送状态栏显示"推送失败"。

**排查步骤**：

1. **确认简报已生成**（`gen_status = 'succeeded'`）。

2. **检查钉钉 webhook 可达性**：

   ```bash
   # 在内网 worker 容器内测试（不要在公网机器上执行，凭据仅内网使用）
   curl -I https://oapi.dingtalk.com/robot/send?access_token=...
   # 预期 HTTP 200
   ```

3. **测试推送**：到 `/admin/briefing/targets` 点击对应目标的"测试推送"按钮，观察结果。

4. **手动重新推送**（admin 权限）：

   ```bash
   curl -X POST https://fe-radar.internal/api/briefing/<id>/repush \
     -H "Cookie: <admin-auth-cookie>"
   # 或在 /briefing/[id] 详情页点击"重新推送"按钮（admin 可见）
   ```

5. **如仍失败**：检查 Pino 日志中 `dingtalk_bot` 相关 error（`webhook_url` 字段已 redact 为 `[REDACTED]`，需核对 Grafana errcode）：
   - `errcode: 310000`：参数错误，检查 actionCard 格式
   - `errcode: 300001`：IP 未在白名单（如使用 IP 白名单模式而非加签模式）
   - HTTP `401`：sign_secret 已过期或错误 → 按第 2 节轮换凭据

## 5. 监控告警响应

以下 4 条 Grafana 告警规则（`deploy/grafana/provisioning/alerts/commodity-briefing.yaml`）：

### 5.1 briefing-gen 连续 2 日失败（红色）

**应对**：

1. 查 Loki 日志确认根因（见 §4.1 排查步骤）
2. 若是 adapter 失效（交易所页面改版）→ 临时禁用失效 source，触发降级生成（字段显示"—"），同时建 issue 修复 adapter
3. 若是 Kimi 服务故障 → 联系 LLM 运维，等服务恢复后手动重推
4. 解决后在 Linear 对应 issue 留评论记录根因

### 5.2 briefing-push 当日失败率 > 50%（红色）

**应对**：

1. 立即到 `/admin/briefing/targets` 检查各目标状态
2. 点击"测试推送"定位失效目标
3. 若是凭据问题 → 按第 2 节轮换凭据
4. 若是钉钉平台故障 → 等平台恢复后手动重推（当日简报数据已落库，不会丢失）

### 5.3 第一层字段连续 3 工作日缺失（红色）

**应对**：

1. 查询 `commodity_quotes` 确认哪些 `metric_key` 连续缺失：
   ```sql
   SELECT metric_key, COUNT(*) as miss_days
   FROM (
     SELECT generate_series(CURRENT_DATE - 4, CURRENT_DATE, '1 day'::interval)::date AS d
   ) days
   LEFT JOIN commodity_quotes q ON q.observed_at::date = days.d AND q.value IS NULL
   GROUP BY metric_key HAVING COUNT(*) >= 3;
   ```
2. 找到对应 source（`sources WHERE fetcher_type='quotes'`），检查 adapter 是否失效
3. 按 §4.1 步骤 3 处理

### 5.4 RSSHub 容器 health 失败（红色）

**应对**：

1. 检查 Portainer 中 `rsshub` 服务状态：
   ```bash
   docker service ps fe-radar_rsshub
   ```
2. 若容器退出（exit code 非 0）→ 查日志：
   ```bash
   docker service logs fe-radar_rsshub --tail 50
   ```
3. 强制重启：
   ```bash
   docker service update --force fe-radar_rsshub
   ```
4. 若持续崩溃（OOM / 镜像问题）→ 检查内存分配（rsshub 配额 256MB）；镜像问题需 pin 到稳定 digest 后重新 deploy
5. RSSHub 仅影响 T2 RSSHub 包装的信源（SMM / 生意社 / 长江有色 / 中汽协），T1 交易所直连不受影响；简报会降级生成（缺失字段标"—"），触发黄色告警

## 6. 数据保留策略

| 数据类型             | 表 / 存储                         | 保留期                                          | 清理机制                                                                    |
| -------------------- | --------------------------------- | ----------------------------------------------- | --------------------------------------------------------------------------- |
| 大宗商品时序数值     | `commodity_quotes`                | **365 天**                                      | v1.0 cleanup job 每日 DELETE（`observed_at < now() - INTERVAL '365 days'`） |
| 简报元数据 + payload | `commodity_briefings`             | **90 天**                                       | cleanup job DELETE（`briefing_date < now() - INTERVAL '90 days'`）          |
| 简报推送记录         | `briefing_pushes`                 | 跟随 `commodity_briefings`（ON DELETE CASCADE） | 随 briefings 级联删除                                                       |
| 简报 docx 文件       | MinIO `fe-radar-briefings` bucket | **≤ 90 天**                                     | MinIO bucket lifecycle policy（Objects 自动过期 · 不由 cleanup job 处理）   |
| 推送目标配置         | `briefing_targets`                | **永久**（软删 disabled_at）                    | 不进入 cleanup；配置类数据永久保留                                          |
| 节假日表             | `briefing_holidays`               | **永久**                                        | 不进入 cleanup                                                              |
| 模板字段映射         | `briefing_template_fields`        | **永久**                                        | 不进入 cleanup                                                              |

**重要**：

- `commodity_quotes` 保留 365 天（超 v1.0 默认 90 天），因价格历史具有研判价值（NFR-103）
- docx 文件超过 90 天后，`/briefing/[id]` 下载按钮显示灰态"已过保留期"，API 返回 **410 Gone**（`code: BRIEFING_DOCX_EXPIRED`），不是 404
- MinIO lifecycle policy 须在首次部署时手动配置（见第 3 节步骤 8），否则 docx 文件不会自动清理

## 7. 项目代号字典（project_codes）维护 SOP

**背景（S4 / T-SEC-09）**：公网 LLM（DeepSeek / Kimi）调用前，`packages/core/scrubber.ts` 会把正文中的**真实项目代号**替换为 `[REDACTED:PROJECT_CODE:…]`。字典源是 `project_codes` 表；**没有 UI**，admin 通过本 API 维护。字典本身**不会**进入 LLM 请求体，只作为 scrubber 匹配列表。

**行为语义（worker `loadProjectCodes`）**：

| 状态                     | 行为                                     |
| ------------------------ | ---------------------------------------- |
| 表/查询从未成功加载过    | **阻断**公网 LLM job（失败，不静默放行） |
| 曾加载成功、本次 DB 抖动 | 沿用上次快照（防一次抖动清空字典）       |
| 加载成功但表为空         | **放行**（合法：admin 尚未配置代号）     |

worker 缓存 TTL 5 分钟；新增/软删后最迟 5 分钟生效，无需重启。

### API（admin only，`requireFreshRole(..., "admin")`）

基路径：`/api/admin/project-codes`（需已登录 admin 会话 cookie）。

```bash
# 列表（含已软删）
curl -sS -b 'fe-radar.session-token=...' \
  'http://<host>/api/admin/project-codes'

# 新增
curl -sS -b 'fe-radar.session-token=...' \
  -H 'content-type: application/json' \
  -d '{"code":"ZX-2026","note":"内部项目示例"}' \
  'http://<host>/api/admin/project-codes'

# 改 note / 重命名 / 重新启用
curl -sS -b 'fe-radar.session-token=...' \
  -X PATCH -H 'content-type: application/json' \
  -d '{"id":1,"note":"更新","enabled":true}' \
  'http://<host>/api/admin/project-codes'

# 软删（disabled_at=now；等价 enabled=false）
curl -sS -b 'fe-radar.session-token=...' \
  -X DELETE 'http://<host>/api/admin/project-codes?id=1'
```

**上线检查**：新环境 migrate 含 `0058_project_codes` 后表为空是合法状态（放行）；务必在生产写入真实代号，否则脱敏对该类字符串无效。若表缺失或 worker 启动后从未成功加载，pipeline / daily-gen / briefing-gen 会失败并打结构化错误日志，而不是把真实代号送出网。
