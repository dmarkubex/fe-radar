# 背景（第八轮全量 diff 复审，未逐一独立复现但代码路径已核实为真，采信 codex 发现）

`deploy/compose.portainer-current.yml:62` 与 `deploy/compose.fetch-smoke.yml:65`
都把 migrate 和 seed:admin **绑定成同一条部署命令**：
`pnpm --filter @fe-radar/db migrate && pnpm --filter @fe-radar/db seed:admin`。
也就是说**每一次 Portainer 部署**（哪怕只是改了个不相关的信源配置、跟 admin 账号
完全无关）都会重跑 `seed:admin`。

`upsertAdmin`（:30 附近）：

```ts
await sql`
  INSERT INTO users (username, password_hash, name, dept, role)
  VALUES (${user.username}, ${passwordHash}, ${user.name}, ${user.dept}, ${user.role})
  ON CONFLICT (username) DO UPDATE SET
    password_hash = EXCLUDED.password_hash,
    name          = EXCLUDED.name,
    dept          = EXCLUDED.dept,
    role          = EXCLUDED.role,
    token_version = users.token_version + 1
`;
```

`token_version` **无条件** `+1`——即使 `SEED_ADMIN_PASSWORD` 环境变量这次部署跟上次
完全一样（没有真的轮换密码），每次部署仍然会把 admin 的 `token_version` 递增，
根据 `token-freshness.ts` 的撤权链设计（本项目多轮修复过的核心机制），这会让
admin 当前所有已登录会话在下次请求时被判定为"过期"、强制重新登录。**文件自己的
注释已经承认这是已知行为**（"每次重跑 seed 都视为一次轮换……不要把 seed:admin
当无害的幂等脚本随手重跑"），但 compose 文件把它和 migrate 绑死，运维在日常部署里
很难避免触发它——这不是"文档提醒了就没事"，是设计与实际部署流程脱节。

## 修法要求（注意踩坑：不能用 SQL 直接比较 bcrypt hash）

**本项目在 V-1（`.ai/reviews/2026-08-10-round6-arbitration.md`）已经踩过一次同类坑**：
bcrypt 每次 `hash()` 都用随机 salt，即使明文密码没变，新算出来的 hash 字符串也**永远
不等于**旧的存量 hash——`WHERE password_hash = ${newHash}` 这种 SQL 字面量比较**恒假**，
不能用它判断"密码是否真的变了"。正确做法必须是应用层 `bcrypt.compare(明文, 旧hash)`。

要求：

1. `upsertAdmin` 改成先 `SELECT password_hash FROM users WHERE username = ${user.username}`
   查出**当前存量 hash**（不存在则视为首次创建，`isChanged = true`）。
2. 若存量 hash 存在，用 `bcrypt.compare(user.password, existingHash)` 判断这次传入的
   明文密码是否等于存量密码对应的明文——**相等**（`compare` 返回 `true`）说明密码没变，
   `isChanged = false`；不相等或不存在存量记录，`isChanged = true`。
3. 把 `isChanged` 结果传给后续的 `INSERT ... ON CONFLICT DO UPDATE`，`token_version` 的
   递增量根据 `isChanged` 决定（`isChanged` 为 `false` 时 `token_version = users.token_version`
   即保持不变；为 `true` 时才 `+1`）——用应用层算出的布尔值拼进 SQL（例如把
   `isChanged ? sql\`token_version + 1\` : sql\`token_version\``用`postgres`包支持的
动态片段写法拼接，具体写法自行决定，只要保证语义正确、类型检查通过）。`name`/`dept`/`role` 三个字段维持无条件更新（这三项不是凭据，改了就该生效，
   不需要走同样的"是否变化"判断，保持现状）。
4. **两次 SELECT+UPDATE 之间存在竞态窗口是可接受的**（这是一次性部署脚本，不是高并发
   服务端点，不需要事务锁或额外并发保护——不要为此引入锁机制，成本收益不对等）。

## 强制机械检查

1. `grep -n "token_version" packages/db/scripts/seed-admin.ts` 确认改动后确实是
   条件递增，不是又写成无条件 `+1`。
2. 回代验算（强制）：
   - 场景 A：首次创建（无存量用户）→ 断言 `token_version` 从默认值起有且仅有一次
     视为"变化"（若默认起始值本来就是某个数，具体断言口径以现有 schema 默认值为准，
     去 `packages/db` migration 里查 `token_version` 列的 `DEFAULT`）。
   - 场景 B：存量用户存在，`SEED_ADMIN_PASSWORD` 与上次相同 → 断言 `token_version`
     **不变**。这是本任务要修的核心场景，必须先确认**修复前**这条测试会红
     （旧逻辑下 `token_version` 每次都 +1），再确认修复后变绿，两次结果都写进最终回复。
   - 场景 C：存量用户存在，密码真的变了 → 断言 `token_version` `+1`（回归，不能破坏
     T-SEC-06 想要的"密码轮换后旧 JWT 立即失效"）。
3. 因为文件当前 `main().catch(...)` 在模块底部无条件执行（import 即触发副作用，
   连真实 `DATABASE_URL` 都没有会直接抛错退出），**新测试不能直接 import 整个模块**。
   需要把 `upsertAdmin`（连同新增的 SELECT+compare 逻辑）重构成可独立 `export` 的
   函数，测试用一个内存态假 `sql` 标签函数模拟 SELECT 返回值 + UPDATE 影响行为，
   参照 `packages/db/scripts/purge-legacy-viewer-branch-b.ts` 与
   `packages/db/src/__tests__/purge-legacy-viewer-branch-b.test.ts` 里已经用过的
   "假 sql 标签函数，检查真实拼出来的 SQL 文本"这个模式（同一个包里已有先例，
   不要另起一套写法）。`main()` 本体保持调用这个新导出函数，行为不变。
