# A-5（High）— admin layout 把 editor 挡在了它本该能进的页面外

## 已观测事实（主会话已验证）

- `apps/web/middleware.ts:21`：`isEditorAdminPage = ["/admin/entities", "/admin/sources"]`
- `apps/web/middleware.ts:78`：这两个路径的 requiredRole 是 **editor**
- 而 S3a 新建的 `apps/web/app/(admin)/layout.tsx` 调 `gateAdminPage()`，
  后者在 `apps/web/lib/auth/token-freshness.ts:177` **无条件 `hasRole(role, "admin")`**

**失败场景**：在职 editor 打开 `/admin/sources` → 通过 middleware（editor 够）→
被 layout 返回 403 → **无法维护信源和实体**。这是 S3a 引入的功能回归。

## 要做的事

让 layout 的角色要求与 middleware 的路由策略一致：
`/admin/entities` 与 `/admin/sources` 要求 editor，其余 admin 页要求 admin。

middleware 已注入 `x-pathname` 请求头（见 `middleware.ts`），可据此做同源角色映射；
或给这两个页面拆嵌套 layout。**两种做法都可以，但必须让"路由 → 所需角色"只有一处权威定义**，
不要在 middleware 和 layout 里各写一份清单——本项目最高发的缺陷就是这类镜像不一致。

# A-4（High）— IP 维度限速永不执行

## 已观测事实

`apps/web/auth.ts:62-66` 用 `(request as { ip?: string })?.ip` 取 peer 地址。
但 Auth.js 传入 `authorize()` 的是**标准 Web `Request`**
（`@auth/core/src/providers/credentials.ts:73` 明确声明 `request: Request`），
Web Request **没有 `.ip` 属性**。

叠加 `TRUST_PROXY_HEADERS` 默认关闭（`deploy/stack.yml:11`）→ XFF 也被忽略
→ `resolveLoginClientIp(null, null)` 返回 null → **IP 维度被永久跳过**。

**失败场景**：同一来源轮换企业用户名喷洒密码。每个用户名仍限 5 次，
但共享 IP 上限完全不生效，可依次攻击全部账号。

## 要做的事

**先判断哪条路可行，把判断依据写进 handoff.md：**

- (a) 若能在 Next.js 层面拿到真实对端地址（如 route handler 层而非 Auth.js `authorize()` 内），
  把 IP 限速上移到那一层；
- (b) 若拿不到，则**如实承认当前部署下 IP 维度不可用**——删掉这段永远为 null 的代码，
  在注释与 runbook 写明"IP 维度需前置可信反向代理后才能启用"，
  并把 `TRUST_PROXY_HEADERS` 的启用条件写进部署文档。

**不要保留一段永远不生效却看起来在工作的代码** —— 这正是本批次 X-1 的教训。

# A-7（Medium）— 空字符串 AUTH_URL 遮蔽有效的 NEXTAUTH_URL

`apps/web/instrumentation.ts` 用 `process.env.AUTH_URL ?? process.env.NEXTAUTH_URL`。
`??` 只在 null/undefined 时回退，**空字符串会被当作有效值**。

**失败场景**：Portainer 里遗留 `AUTH_URL=""`、同时正确设了 `NEXTAUTH_URL=http://10.1.20.156:3013`
→ 启动校验读到空值抛错 → web 容器重启循环。

修法：取两者中**第一个 `trim()` 后非空**的值。
同样检查 `apps/web/auth.ts:28` 附近有无同一模式（镜像校验）。
