## 背景

`packages/db/migrations/0061_legacy_viewer_credential_purge.sql` 目前两个分支：

```sql
-- A: 已绑钉钉且仍有 password_hash → 清 password_hash + bump token_version（不禁用）
-- B: 未绑钉钉且仍启用 → disabled_at = NOW + bump token_version
```

## 已观测缺陷（主会话已验证，不是假设）

bcrypt hash 每次生成都带随机盐，**SQL 层面不可能比对某个 `password_hash` 字段
是否等于"仓库已知的泄漏默认口令"对应的 hash**。两个分支的判定条件
（"是否存在 password_hash"、"是否被禁用"）只看**状态**，不看**内容**——
无法区分"仍是原始泄漏口令"和"admin 后来已经正常轮换过的强口令"。

两个分支的实际风险不对等：

- **分支 A**（已绑钉钉）：误清一个合法轮换过的本地密码 → 账号仍可经钉钉 SSO 登录，
  只是本地应急登录 fallback 被清空。**影响可控，本任务不要求修 A**。
- **分支 B**（未绑钉钉）：若生产存在一个"曾被禁用、后被 admin 合法重新启用、
  用户名恰为 `viewer`"的纯本地账号，**首次应用该迁移时会把它重新禁用**，
  无任何区分信号、无绕过路径（该账号没绑钉钉，退不到 SSO）。**这是完全锁死**。
  `migrate.ts` 有 checksum ledger 能防止**重跑**清空，但防不住**首次应用时判断本身就错**。

## 要做的事

**纯 SQL 无法安全解决这个问题**（bcrypt 比对不了）。改成应用层脚本，
不再是自动执行的 migration：

1. 新建 `packages/db/scripts/purge-legacy-viewer-branch-b.ts`（脚本名可自定，
   语义清晰即可），逻辑：
   - 查询候选行：`username='viewer' AND dingtalk_id IS NULL AND disabled_at IS NULL`
   - 对每一行，用 `bcrypt.compare(<已知泄漏口令明文>, row.password_hash)` 判断
     **是否真的是那个泄漏口令**
   - 只对 `bcrypt.compare` 返回 `true` 的行执行禁用 + bump token_version
   - 对返回 `false` 的行（说明口令已被合法轮换），**跳过并打印一行明确日志**
     （账号 id/username，不打印密码或 hash），提示需要人工确认
2. **已知的泄漏口令明文**：主会话已核实为 `viewer-password`
   （见 `packages/db/migrations/0059_disable_legacy_viewer_credential.sql:2`、
   `packages/db/scripts/seed-admin.ts:48`、既有测试
   `packages/db/src/__tests__/migration-0059-legacy-viewer.test.ts:10` 三处独立确认
   一致）。直接使用这个字符串，**不要再去别处确认或改用其它值**。
   若你在实施中发现证据与此不符（例如某处引用了不同的明文），停下写进 handoff.md，
   不要自行判断哪个是对的。
3. `0061_legacy_viewer_credential_purge.sql` 的**分支 A 保持不变**（本任务不修 A，
   已裁定风险可控）；**分支 B 从迁移 SQL 里删除**，改为在迁移文件注释里说明
   "分支 B 改为应用层脚本 `<脚本路径>`，需在应用迁移后由运维手动执行一次，
   不属于自动 migration 流程的一部分"。
4. **写一份简短的运维步骤说明**（加进 `docs/runbook/deploy-portainer.md` 或
   0061 迁移文件头注释均可，你判断放哪里更合适并说明理由）：
   "应用 0061 后，运维需手动运行 `purge-legacy-viewer-branch-b.ts`，
   review 输出中被跳过的行（如有），逐个人工确认该账号是否需要保留。"
