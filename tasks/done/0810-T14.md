# 缺陷 V-1（Critical）— purge 脚本对真实数据库完全空转，SQL 字段名与 TS 接口不匹配

## 已观测缺陷（裁判已验证，非假设）

`packages/db/scripts/purge-legacy-viewer-branch-b.ts:118`：

```ts
return sql<CandidateRow[]>`
  SELECT id, username, password_hash
  FROM users
  WHERE username = 'viewer'
    AND dingtalk_id IS NULL
    AND disabled_at IS NULL
`;
```

`CandidateRow` 接口（:35 附近）的字段是 `passwordHash`（camelCase），
但 SQL 查询返回的列名是 `password_hash`（snake_case），**没有 `AS "passwordHash"` 别名**。

**裁判已核实**：本项目全部 `postgres(...)` 客户端实例化
（`packages/db/src/client.ts`、`seed-admin.ts`、`migrate.ts` 等 8 处）
**均未配置 `transform` 选项**。`sql<CandidateRow[]>` 泛型标注只是 TypeScript 编译期
类型断言，**不产生任何运行时字段名转换**。

**失败场景**：真实数据库前，每一行返回的对象实际字段是 `row.password_hash`，
读 `row.passwordHash`（:60 `decidePurge` 函数）永远得到 `undefined`：

```ts
if (!row.passwordHash) {
  return { row, shouldDisable: false }; // 每一行真实数据都会命中这里
}
```

`bcrypt.compare` 永远不会被调用。脚本会正常跑完，对每一行打印
`"SKIP ... — password does not match leaked default; likely already rotated."`——
这段日志措辞暗示"已核实、确认已轮换"，**但实际从未做过任何比对**。
运维会误以为系统正确工作，实际上泄漏默认口令的账号永远不会被这个脚本禁用——
本脚本原本要闭环的漏洞（A-3/B-3）在应用层从未真正生效。

## 要做的事

1. 修 SQL 查询，加列别名：`SELECT id, username, password_hash AS "passwordHash"`。
   **`postgres` 包的双引号别名语法保留大小写**，确认这个写法能让运行时返回的字段
   确实是 `passwordHash`（若不确定这个具体语法在这个 `postgres` 版本下是否生效，
   在 handoff.md 说明你的判断依据；优先选择这个方案而不是改用其它方案，
   因为改动最小、不影响其它查询）。
2. **补一条真正覆盖这个 bug 的测试**——不能只测 `decidePurge` 纯函数
   （现有测试已经这样做了，但对这个 bug 零覆盖，因为测试直接手写
   camelCase 对象绕过了真实 SQL 返回值格式）。新增一条测试，模拟一个
   "真实 SQL 返回原始字段名格式"的场景：构造一个假的 `sql` 标签函数
   （或直接测试 `fetchCandidates` 函数本身，若它当前不可测试则重构为可注入 `sql` 参数），
   传入模拟返回 `password_hash`（snake_case）的行数据，断言最终交给 `decidePurge` 的对象
   确实有 `passwordHash` 字段且值正确，**不是 `undefined`**。
   这条测试在修复前必须是红的——先确认当前代码在这个场景下确实会得到 `undefined`。
3. **检查项目里有没有第二处同样的 snake_case SQL 列名 + camelCase TS 接口不匹配**
   （见下方机械检查）。

# 缺陷 V-2（High）— CI 门禁与 worker 判定集合不一致，缺 limit 截断

## 已观测缺陷

`apps/worker/src/fetchers/playwright.ts:222` 附近：

```ts
nodes.slice(0, limit).map((node) => {...})   // 真的做了截断，limit = clamp(config.limit ?? 20, 1, 50)
```

`packages/db/scripts/verify-sources.ts:187` 附近：

```ts
const items = els.map((node) => {...})   // 没有 slice，判定全部匹配元素
```

单条有效性判定逻辑（标题非空、link 非空、link 是否回退成 listUrl 本身）两处逐字符一致，
但**被判定的元素集合不同**——B-5 想要的"CI 门禁与运行时统一判定口径"在元素数 > limit 时不成立。

**失败场景**：某列表页 `itemSelector` 命中 40 个节点，前 20 个（worker 的 limit）
是改版后失配的占位/导航节点（空标题），后 20 个正常。`verify:sources` 因为看了全部 40 个、
判定 `valid>0` → CI 门禁绿；worker 只扫前 20 个、全部无效 → 抛 `FETCH_PLAYWRIGHT_EMPTY` →
`fail_count` 累积至上限后源被自动禁用——**CI 门禁本该在这种情况下预警却保持绿灯**，
运维在"CI 全绿"的错觉下不会发现问题，直到源真的被禁用才会注意到。

## 要做的事

`verify-sources.ts` 的对应校验函数补上与 `playwright.ts:218` 相同的 limit 计算与截断：

```ts
const limit = Math.min(Math.max(config?.limit ?? 20, 1), 50);
```

`$$eval` 传入的回调里，`els.map(...)` 改为 `els.slice(0, limit).map(...)`；
`matched` 字段也应反映**截断后**的数量（与 worker 侧 `extracted.length` 语义一致），
不是原始 DOM 匹配总数。

## 允许修改的文件（清单外即越界）

```

packages/db/src/__tests__/verify-sources.test.ts
handoff.md
```

## 必须新增的测试

40 个匹配节点、前 20 个标题为空、后 20 个正常 → CI 判定应为无效（`valid=0` 或等价的
门禁失败结果），**不应该**因为全集里有有效元素就判定通过。这条在修复前必须是红的。

# 缺陷 V-3（Medium）— 应用层脚本禁用操作有 TOCTOU 窗口

## 已观测缺陷

`packages/db/scripts/purge-legacy-viewer-branch-b.ts:135` 附近：

```ts
UPDATE users
SET disabled_at = COALESCE(disabled_at, NOW()),
    token_version = token_version + 1
WHERE id = ${row.id}
```

只按 `id` 约束，不复验 UPDATE 时刻 `password_hash`/`dingtalk_id`/`disabled_at`
是否仍是 SELECT 时读到的状态。bcrypt(cost=12) 比对耗时数百毫秒，
此窗口内若 admin 恰好轮换了该账号的密码或绑定了钉钉，UPDATE 仍会按陈旧快照执行禁用。

## 要做的事

`disableCandidate` 函数的 UPDATE 加上与读取时一致的约束条件：

```sql
UPDATE users
SET disabled_at = COALESCE(disabled_at, NOW()),
    token_version = token_version + 1
WHERE id = ${row.id}
  AND username = 'viewer'
  AND dingtalk_id IS NULL
  AND disabled_at IS NULL
  AND password_hash = ${row.passwordHash}
```

（注意：这条依赖 V-1 修好之后 `row.passwordHash` 才是真实值——两条缺陷有先后依赖，
V-1 必须先修。）

`postgres` 库的 UPDATE 返回值可以判断实际受影响行数（如 `.count` 或返回数组长度，
视 `postgres` 包 API 而定，你需要确认正确用法）。**若 UPDATE 影响行数为 0**
（说明状态已在窗口期间变化），打印一条明确日志（账号 id/username，不打印密码/hash），
提示"状态已变化，本次未禁用，需人工复查"，计入 `skipped` 而不是 `disabled`。

```

packages/db/src/__tests__/purge-legacy-viewer-branch-b.test.ts

```

## 必须新增的测试

1. UPDATE 条件里加了状态复验后，正常场景（状态未变化）仍能正确禁用——回归测试。
2. 模拟 UPDATE 影响 0 行的场景（状态已变化）→ 断言记为 `skipped` 而非 `disabled`，
   且有对应的明确日志。
