# 背景（第八轮全量 diff 复审，裁判已独立核实为真）

`packages/core/src/url-guard.ts` 的 `FETCH_INTERNAL_ALLOWLIST` 机制（T-SEC-12）
是为了让容器内部服务（如 RSSHub `rsshub:1200`）豁免 SSRF 的私网 IP 检查——
这些 hostname 本来就该解析到内网，不算攻击面。这个豁免只作用于 SSRF 判定
（`assertPublicFetchUrl`/`isInternalAllowlisted`），**跟代理池是两条完全独立的逻辑**。

`apps/worker/src/fetchers/http.ts` 的 `fetchTextWithPolicy`（:211 起）：

```ts
let proxy = proxyPool.acquire();   // :239，无条件调用，不管目标 hostname 是不是 allowlist 内部服务
...
const dispatcher = buildDispatcher(proxy?.server, insecureTLS);  // :255
```

`buildDispatcher`（:87）只要 `proxy.server` 非空就会构造一个指向**外部代理服务器**的
`ProxyAgent`，把这次请求的实际出网路径钉死在那个外部代理上。

**失败场景**：`PROXY_POOL_ENABLED=true`（项目 T1 信源计划走代理池，见项目
CLAUDE.md"代理池仅用于绕 IP 封禁"一节）+ 某个 quotes/RSSHub 类信源的 URL 是
`FETCH_INTERNAL_ALLOWLIST` 里配置的内部 hostname（如 `http://rsshub:1200/xxx`）。
这次 fetch 依然会走 `proxyPool.acquire()` 拿到一个外部代理、构造指向它的
`ProxyAgent`——**外部代理服务器根本无法解析/连接 Docker compose 网络内部的
`rsshub` 这个 hostname**，请求必然失败（DNS 解析失败或连接被拒绝，取决于代理
自身的报错行为），且会走进现有的失败重试分支反复重试、最终耗尽 2 次 attempt
后仍然失败——内部 RSSHub 信源在代理池开启后会**持续断供**，且报错信息
（普通网络错误）完全看不出根因是"内部 hostname 被误塞进了外部代理"。

**修法**：在 `fetchTextWithPolicy` 里，`proxyPool.acquire()` 之前先判断目标 URL
的 hostname 是否命中 `isInternalAllowlisted()`（从 `@fe-radar/core` 导入，
文件已经 import 了这个函数，见 :2）——命中则整个函数跳过代理池，`proxy` 恒为
`undefined`，后续 `buildDispatcher(undefined, insecureTLS)` 自然直连不经代理；
未命中走原有逻辑不变。注意 `followRedirectsWithGuard` 内部会对每一跳
`Location` 重新调 `assertPublicFetchUrl`（:198），但**不会**重新判断 allowlist
对代理选择的影响——重定向到 allowlist 内部服务这个变体本次不要求处理（超出本任务
范围，若顺手做了要在回复里说明并给出对应测试，不做也不算未完成）。
