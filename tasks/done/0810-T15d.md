# 背景（第八轮全量 diff 复审，裁判已用 Node 脚本直接实证复现）

`scrubText`（:36 起）里：

```ts
for (const code of context.projectCodes ?? []) {
  if (code.trim().length === 0) continue;
  cleaned = replaceMatches(
    cleaned,
    "PROJECT_CODE",
    new RegExp(escapeRegExp(code), "g"),
    found
  );
}
```

`context.projectCodes` 按 `loadProjectCodes()`（`apps/worker/src/handlers/context.ts`）
返回的数组顺序原样遍历，**没有按长度排序**。这段脱敏是 T-SEC-09 的核心防线——
公网 LLM 调用前必须把项目代号完全脱敏（本项目 CLAUDE.md 硬约束"公网 LLM 调用前必经
scrubber.ts"），这里的顺序缺陷会导致**部分脱敏、代号碎片残留在发给公网 LLM 的文本里**。

**已实证复现**（裁判直接跑 Node 验证，非推测）：若 `projectCodes = ["ZX", "ZX-2026"]`
（这个顺序，`"ZX"` 排在前面），文本 `"项目 ZX-2026 进展顺利"` 经过这段逻辑后：

1. 先替换 `"ZX"` → `"项目 [REDACTED:PROJECT_CODE:xxxxxxxx]-2026 进展顺利"`
2. 再尝试替换 `"ZX-2026"`（此时文本里已经没有连续的 `"ZX-2026"` 子串了，正则找不到匹配）

结果：**字面量 `"-2026"` 这个真实敏感代号的一部分残留在送去公网 DeepSeek/Kimi 的文本里**，
只是替换了代号的一部分，不是完全遮蔽。若排序改成先处理 `"ZX-2026"`（长的先替换），
结果是完全脱敏、无残留。

## 修法

`for (const code of context.projectCodes ?? [])` 之前，把 `context.projectCodes`
按字符串长度**降序**排序一份副本再遍历（长的代号先替换，短的代号即使是长代号的
子串也不会提前把它"打散"）。不要原地修改 `context.projectCodes`（调用方可能复用
这个数组，参照本文件其它地方处理输入参数的风格，不做原地 mutate）。

## 强制机械检查

1. `grep -n "projectCodes" packages/core/src/scrubber.ts apps/worker/src/handlers/*.ts`
   ——确认没有其它地方假设了这个数组的遍历顺序（不应该有，但排查一遍）。
2. 回代验算（强制）：新增一条测试，复现上面 `["ZX", "ZX-2026"]` 顺序输入
   `"项目 ZX-2026 进展顺利"` 的场景。**先确认这条测试在修复前会红**（`cleaned`
   里含有 `"-2026"` 字面量残留），再验证修复后 `cleaned` 里完全不含任何原始代号的
   任何长度 ≥2 的连续子串（用 `expect(cleaned).not.toContain("ZX")` 和
   `expect(cleaned).not.toContain("2026")` 一类断言，覆盖"完全脱敏"而不是只测
   一个特定子串）。两次结果都写进最终回复。
3. 补一条排序稳定性场景：`projectCodes` 里含多组长度不同且互为子串关系的代号
   （至少 3 个，例如 `["A", "AB", "ABC"]`，任意打乱输入顺序），验证脱敏后
   `cleaned` 不含任何一个原始代号的残留。
