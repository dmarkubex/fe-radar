# 背景（第八轮全量 diff 复审，裁判已独立核实为真，非评审者自述）

三条缺陷都在 `apps/worker/src/fetchers/playwright.ts` 里，**都是"两处独立看都对、
组合起来才错"的跨轮次交互问题**（S1/T5/T13 分三轮改这个文件，历史评审各自过关）。

## 缺陷 1（High）— SSRF 子资源守卫不覆盖弹窗页面

`installSubresourceGuard(page)`（:165 附近）只在单个 `page.route()` 上装守卫，
`page` 对象来自 `browserContext.newPage()`（:105）。**没有任何机制覆盖
`window.open()` 产生的弹窗页面**——弹窗是全新的 Page 对象，`page.route()` 只保护
装它的那一个 Page，Playwright 真实语义里 `context.route()` 才会自动覆盖该 context
下**所有**页面（含未来的弹窗）。

## 缺陷 2（High）— 内容有效性判定用了重定向前的 URL 做基准

`fetchPlaywright`（:120-121）在导航后已经算出 `finalUrl = page.url()`
（重定向后的真实落点，S1/T5 加的 SSRF 复验用途），但这个值**只在 SSRF 复验分支内使用，
从未传给 `extractItems`**。`extractItems` 内部（:249-251）用来判定"href 是否回退成
列表页本身"的 `listUrlNormalized` 变量，用的是 `config.listUrl`（原始、重定向前的 URL）。

**失败场景**：`config.listUrl` = `https://x.com/start`，站点 302 到
`https://x.com/final/`。某条目 `<a href="">`（href 属性存在但为空）——浏览器把空
href 解析成"当前文档地址"（真实 DOM `.href` getter 语义），即 `https://x.com/final/`
（不是空字符串，也不是 `x.com/start`）。这个已解析的绝对地址作为 `item.url` 传回
Node 层，:259 处 `new URL(item.url, config.listUrl)` 因为 `item.url` 已是绝对 URL，
`config.listUrl` 这个 base 参数被忽略，`resolved` = `https://x.com/final/`。
但 :251 处 `listUrlNormalized` = `new URL(config.listUrl).toString()` =
`https://x.com/start`（重定向前）。两者不相等 → "回退列表页"判定**不触发**，
这条本该被过滤的垃圾条目被当成有效条目放行。**凡是站点有重定向，T13 引入的这层
内容有效性检测（B-5/A-6 想堵的"改版后 title/link 失配"）对它完全失效。**

**修法**：把 `finalUrl` 传进 `extractItems`，`listUrlNormalized` 改用
`new URL(finalUrl).toString()`（失败时 fallback 到 `finalUrl` 原样，同现有 catch
写法）。`finalUrl` 的计算需要挪到 `SSRF_GUARD_ENABLED` 判断之外（`page.url()`
本身不依赖守卫开关，`SSRF_GUARD_ENABLED=false` 时也该拿到真实值）——否则守卫关闭时
`extractItems` 拿不到 `finalUrl`。:259 的 `new URL(item.url, config.listUrl)`
建议一并改成 `new URL(item.url, finalUrl)`（`item.url` 目前虽然总是绝对路径，
但改成正确的语义基准更防御性一致，成本为零）。

## 缺陷 3（High）— BrowserContext 池复用时忽略了传入的 UA/代理身份

`fetchPlaywright`（:101-104）：

```ts
const userAgent = acquireUserAgent(context.useRealUa);
await assertRobotsAllowed(config.listUrl, userAgent, robotsFetch ?? fetch);
const proxy = proxyPool.acquire();
const browserContext = await pool.acquire(
  userAgent,
  proxy?.server ? { server: proxy.server } : undefined
);
```

`BrowserContextPool.acquire()`（:54-68）：池未满（`slots.length < MAX_CONTEXTS`，
`MAX_CONTEXTS=2`）时才真正用传入的 `userAgent`/`proxy` 创建新 context；**池满之后
走 round-robin 复用已有 slot，完全忽略本次传入的 `userAgent`/`proxy` 参数**，
返回的是某个更早创建时绑定的、可能完全不同的 UA/代理身份。

**失败场景**：`assertRobotsAllowed` 用**这次新拿到的** `userAgent` 查了 robots.txt
（第 102 行），但真正发起 `page.goto()` 的 `browserContext`（第 104-105 行，池满时）
是用**另一次调用时的旧 UA/代理**创建的——robots 检查的身份和实际发请求的身份对不上。
同时 `proxyPool.release(proxy, true/false)`（:133/:141）总是对**这次新 acquire 出来的
`proxy` 对象**打分（成功/失败），但实际发出请求走的可能是池里另一个 slot 绑定的
**另一个**代理——代理健康度打分被记到了从未真正发出过这次请求的代理身上，
真正在用的代理的失败永远不会被记录、坏代理永远不会被 `proxyPool` 自动禁用。

**修法**：让 `BrowserContextPool` 按 slot 记录**实际绑定**的 `userAgent` 与
`ProxyEndpoint`（不只是 `{server}` 字符串——`proxyPool.release()` 需要完整
`ProxyEndpoint` 引用才能正确打分，见 `apps/worker/src/lib/proxy-pool.ts` 的
`ProxyEndpoint`/`release()` 定义），`acquire()` 返回值从裸 `BrowserContextLike`
改成 `{ context: BrowserContextLike; userAgent: string; proxy?: ProxyEndpoint }`
（新增一个导出接口，命名自定，例如 `PooledBrowserContext`）。

`fetchPlaywright` 调整调用顺序：先 `pool.acquire(requestedUserAgent, requestedProxy)`
拿到**这次实际会用到的**身份（新建 slot 时就是刚请求的这份；复用 slot 时是该 slot
真正绑定的那份），再用**返回值里的** `userAgent` 做 `assertRobotsAllowed`，
`proxyPool.release()` 也用**返回值里的** `proxy`（可能等于也可能不等于 `proxyPool.acquire()`
刚拿到的那个——不等于时说明这次实际用的是另一个 slot 的旧身份，那个"刚 acquire
但没被用上"的 proxy 引用不需要手动释放/复位，`proxyPool` 内部没有"占用状态"，
不 release 它只是不给它记分，无副作用）。

**注意**：`proxyPool.acquire()` 调用顺序需要挪到 `pool.acquire()` **之前**
（现有代码就是这个顺序，不用改），因为要把"这次期望用的身份"作为参数传给
`pool.acquire()`；`pool.acquire()` 内部决定实际返回哪个身份（新建 or 复用）。
