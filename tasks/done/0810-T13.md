## 已观测缺陷

`playwright.ts:220-242`（`extractItems` 附近）只检查抽取结果的**数量**
（`extracted.length === 0`），**不检查每条结果的 title/link 是否真的有效**。

**失败场景**：页面外层容器（`itemSelector`）仍然命中，但站点改版后
内部的标题/链接子选择器失配 → 抽取出的每一条都是空标题或退化成列表页本身的 URL
（`playwright.ts:134-138` 附近 URL 解析逻辑对空 `href` 有回退行为）→
`extracted.length > 0`，不触发 `FETCH_PLAYWRIGHT_EMPTY` → 静默产出一堆
低质量/重复条目，首轮可能因为 URL 相同被去重逻辑吞掉，之后每周期都在写入垃圾数据
或被去重后等效于零产出——但因为不抛错，`fetch.ts` 仍判定为成功，
`verify-sources.ts` 的 CI 门禁（若只看 `itemSelector` 命中数量，不看内容）同样误绿。

即 A-6 想堵的"静默断供"问题，在"selector 命中但内容为空"这个变体下没有完全堵住。

## 要做的事

1. 在 `extractItems` 里，对每条抽取结果做有效性校验：**title 非空（trim 后长度 >0）
   且 link 是合法的、非空的 URL**（不是回退成列表页 URL 本身）。
2. 过滤掉无效条目；**过滤后若结果为空，同样抛 `FETCH_PLAYWRIGHT_EMPTY`**
   （复用已有错误码，不要新造一个）。
3. **区分两种零结果的原因**（写进 error 的 detail/context 里，便于排查）：
   "selector 未命中任何元素" vs "selector 命中但内容全部无效"——
   参考 T5 已有的错误 payload 结构（`{ itemSelector }`），补充第二种场景的信息。
4. 检查 `packages/db/scripts/verify-sources.ts`（T5 已改成读 `itemSelector` 计数）
   是否也需要同步这个"内容有效性"检查，**保持 CI 门禁与运行时判定口径一致**——
   这是本项目最高发的缺陷类型（两处判定标准不同步），务必对齐。

   这条在修复前必须是红的（当前逻辑下 `extracted.length > 0` 会直接放行）。
2. `itemSelector` 命中的元素里部分有效、部分无效（空标题）→ 只保留有效的那部分返回，

4. `verify-sources.ts` 对应同步：命中但内容全空 → 门禁失败（若本任务判断需要同步的话）。
