# 缺陷（High，裁判已独立读代码核实为真）

`BrowserContextPool.acquire()`（约 :82-104）：

```ts
public async acquire(userAgent: string, proxy?: ProxyEndpoint): Promise<PooledBrowserContext> {
  if (this.slots.length < MAX_CONTEXTS) {
    ... // 新建 slot，绑定这次传入的 proxy
  }
  const slot = this.slots[this.cursor % this.slots.length];
  this.cursor += 1;
  ...
  return { context: slot.context, userAgent: slot.userAgent, proxy: slot.proxy };
}
```

池满（`MAX_CONTEXTS=2`）后走纯 round-robin，**完全不检查 `slot.proxy?.disabled`**。

`apps/worker/src/lib/proxy-pool.ts` 的 `ProxyPool.release(proxy, false)`（:59-73）
在某个 `ProxyEndpoint` 连续失败达到 `failThreshold` 后会把它标记
`proxy.disabled = true`。T15a 修复之前，`fetchPlaywright` 对**错误的 proxy 对象**
打分（池身份不匹配那条缺陷），所以即使某个 slot 实际用的代理一直失败，
真正该被标记禁用的那个 `ProxyEndpoint` 对象也从未被正确打上 `disabled`——
这个"池子从不检查禁用状态"的问题被那个更早的 bug 意外掩盖了，从未真正暴露。

**T15a 把打分对象修正为 slot 实际绑定的 proxy 之后，禁用标记现在能正确落到位了，
但 `acquire()` 的 round-robin 选择逻辑从未跟着补上"跳过已禁用"的判断**——
于是出现一个新的、可复现的失败链：

**失败场景**（裁判已直接读代码确认逻辑成立）：

1. 池内两个 slot，slot A 绑定 proxy P1，slot B 绑定 proxy P2。
2. P1 通过 P1 发起的请求连续失败，`proxyPool.release(P1, false)` 累计到
   `failThreshold`，`P1.disabled = true`。
3. 下一次 `fetchPlaywright` 调用，`proxyPool.acquire()` 因为 P1 已禁用，
   合理地返回一个健康代理 P3（`requestedProxy = P3`）。
4. 但池已满，`pool.acquire(userAgent, P3)` 走 round-robin，游标转到 slot A，
   **直接返回 slot A 绑定的 `{context, userAgent, proxy: P1}`——无视 P1 已禁用、
   无视这次其实拿到了健康的 P3**。P3 被静默丢弃（不使用也不 release）。
5. 这次请求实际用 P1（已禁用的坏代理）发出，`proxyPool` 关于"P1 不健康"的判断
   完全没有影响到 playwright 抓取的实际路径——代理健康度跟踪机制对
   playwright fetcher 形同虚设，一旦某个 slot 绑定的代理变坏，那个 slot
   会永远用坏代理跑下去，直到进程重启（池只在 `pool.close()` 时清空）。

## 修法

`acquire()` 的池满分支需要：

1. 优先寻找一个 `proxy?.disabled` 不为 `true` 的 slot（可以先看 round-robin 選中的
   那个 slot 是否健康；不健康则在其余 slot 里找一个健康的）。
2. 如果找到一个健康 slot，返回它（不必强求"轮转公平"，避免坏代理是优先目标）。
3. **如果所有 slot 绑定的代理都已禁用**（或都没配代理），走一次"就地重建"：
   关闭该 slot 原来的 `context`（`await slot.context.close()`，`browser` 不需要关闭/
   重建，同一个 `browser` 可以开新 context——若你核实 `BrowserLike` 接口只暴露了
   `newContext`，直接在同一个 `browser` 上再开一个新 context 即可，不需要连
   `browser.close()`/重新 launch），用**这次实际传入的 `proxy` 参数**（可能是
   `undefined`，即直连）新建一个 context 替换这个 slot（保留 slot 在数组里的位置，
   更新 `context`/`userAgent`/`proxy` 三个字段），并对这个新 context 重新调用一次
   `installSubresourceGuard`（SSRF 守卫是挂在 context 上的，换了 context 必须重装，
   否则新 context 没有 SSRF 保护）。
4. 步骤 3 属于"确实没有更好选择时的兜底"，不要求每次 proxy 换了就重建——
   只在**当前 round-robin 选中的 slot 已禁用、且没有其它健康 slot 可用**时才触发。

**关于何时判定"没有更好选择"**：只要遍历一遍 `this.slots` 数组，全部
`proxy?.disabled === true`（或全部没绑代理，即 `proxy === undefined` 且这次也没有
新代理可用），就走步骤 3；只要还有一个 slot 的代理是健康的，走步骤 1-2。
