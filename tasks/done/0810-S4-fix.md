## 背景（生产代码是对的，不要回滚它）

S4 把 `apps/worker/src/handlers/context.ts` 的 `loadProjectCodes()` 改成三态：
从未成功加载过且本次 DB 失败 → **抛错，阻断公网 LLM 调用**。**这是有意的安全修复，行为正确，不要动。**

后果：测试环境没有 `DATABASE_URL`，`getDb()` 抛 `"DATABASE_URL is required"`，
而测试进程从未成功加载过快照 → `loadProjectCodes()` 正确地抛错 →
所有走公网 LLM 路径的 job 测试失败。

实测现状（在 `apps/worker` 目录）：

```
Tests  11 failed | 486 passed
  src/jobs/__tests__/briefing-gen.test.ts   10 failed
  src/jobs/__tests__/daily-gen.test.ts       1 failed

堆栈：runBriefingGen → loadProjectCodes (handlers/context.ts:191)
      → getDb() → Error: DATABASE_URL is required
      → "loadProjectCodes failed with no prior snapshot; blocking public LLM calls"
```

**失败的是测试没有为新的 fail-closed 语义做准备，不是生产代码有问题。**

## 要做的事

给这两个测试文件补上对 `loadProjectCodes` 的处理，让它们能走到被测逻辑。

**推荐做法**：`vi.mock("../../handlers/context")`（或对应相对路径）把 `loadProjectCodes`
mock 成返回一个确定的代号数组，例如 `["ZX-01"]` 或 `[]`。
这样测试意图（验证 briefing-gen / daily-gen 的生成逻辑）保持不变，不被 DB 可用性污染。

**不要**用以下方式绕过：

- 在测试里设 `process.env.DATABASE_URL`（会让测试真去连库，慢且不稳定）
- 把 `loadProjectCodes` 的 fail-closed 改回 fail-open（那是回滚安全修复）
- 给 `context.ts` 加"测试环境跳过"分支（生产代码不该知道测试的存在，且这类开关本身是绕过口）
