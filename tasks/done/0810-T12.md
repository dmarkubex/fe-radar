## 已观测缺陷（主会话已验证）

`apps/web/lib/auth/login-rate-limit.ts:37` 附近：

```ts
let client: IORedis | null = null;

function getClient(): RedisEvalLike | null {
  if (process.env.DISABLE_LOGIN_RATE_LIMIT === "true") return null;
  if (client) {
    return client as unknown as RedisEvalLike;   // 只判非空，不判连接状态
  }
  const url = process.env.REDIS_URL ?? "redis://localhost:6379";
  client = new IORedis(url, {
    connectTimeout: 3000,
    retryStrategy: () => null,   // 禁止重连
    maxRetriesPerRequest: 1,
    lazyConnect: true
  });
  ...
}
```

`if (client)` 只检查变量是否非空，**不检查这个客户端实例当前是否处于可用连接状态**。
`retryStrategy: () => null` 让 ioredis 永不自动重连。

**失败场景**：任意一次 Redis 短暂中断（网络抖动、Redis 自身重启/维护）导致该客户端
进入 `end` 状态后，之后每次 `getClient()` 调用都返回这个**永久死掉**的实例，
`.eval()` 失败触发既有的 fail-open 逻辑（`admitLoginAttempt` 的 catch 分支）——
登录限速从"故障期间放行"变成"直到 web 容器重启前永久放行"，
即使 Redis 早已恢复正常，限速也不会自动恢复。

**注意：fail-open 本身是有意设计**（Redis 不可达时不能锁死全员登录），
**本任务不是要移除 fail-open**，是要让它只在真正故障期间生效，
Redis 恢复后限速应自动恢复。

## 要做的事

1. 给 `client` 加连接状态感知：监听 `IORedis` 的 `end`（或 `close`）事件，
   触发时清空模块级 `client` 引用（设为 `null`），使下次 `getClient()` 调用
   会重新 `new IORedis(...)` 建一个新连接，而不是复用死实例。
2. **保持现有的 `retryStrategy: () => null` 不变**——不是要让 ioredis 自动重连
   （那样会在 Redis 长期不可用时不断重试拖慢请求），而是让下一次业务请求
   触发一次全新的连接尝试。这个尝试若仍失败，走既有 fail-open 路径，
   下次业务请求再重试建连——自然形成"故障期间持续放行 + 一旦恢复立即生效"的行为。
3. **不要引入定时轮询/心跳**（没必要的复杂度，见任务单原则：能用事件驱动就不用轮询）。

## 必须新增的测试

1. **核心用例**：模拟客户端进入 `end` 状态（触发 `end` 事件）后，下一次
   `admitLogin`/`recordLoginFailure` 调用应该**重新建一次新连接**
   （断言 `IORedis` 构造函数被再次调用，或等价的可观测行为），
   而不是继续复用旧的死实例。这条在修复前必须是红的——先确认旧逻辑下
   同一个死 client 会被无限复用。
2. 回归：正常连接场景下不应频繁重建 client（只在真正 `end` 之后才重建，
   不要变成每次调用都新建连接——那样会失去连接复用的意义）。
3. 回归：`DISABLE_LOGIN_RATE_LIMIT=true` 时行为不变（直接返回 null，不建连接）。
