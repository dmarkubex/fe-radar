## 背景

本项目有一个出网 SSRF 守卫 `packages/core/src/url-guard.ts`，用于阻止 worker 抓取
内网 / loopback / 云 metadata 地址。**该守卫目前对 IPv4-mapped IPv6 地址完全失效。**

## 已观测失效的原始数据（必须回代验算）

以下是实际执行生产代码 `assertPublicFetchUrl` / `isPrivateIp` 得到的真实输出，
**不是推测**：

```
assertPublicFetchUrl("http://[::ffff:127.0.0.1]/")           -> {"allowed":true,"reason":"PUBLIC_IP_LITERAL"}
assertPublicFetchUrl("http://[::ffff:169.254.169.254]/x")    -> {"allowed":true,"reason":"PUBLIC_IP_LITERAL"}
isPrivateIp("::ffff:7f00:1")    = false     // 这是 127.0.0.1
isPrivateIp("::ffff:a9fe:a9fe") = false     // 这是 169.254.169.254
isPrivateIp("127.0.0.1")        = true      // 点分形式才被识别
```

完整核验记录见 `.ai/reviews/2026-08-10-tsec-batch-adversarial-review.md` 的 V-1 节。

### 根因（已逐环验证，不要重新调查，直接修）

1. WHATWG URL 解析器把 IPv6 字面量规范化成**十六进制组**形式。Node 实测：
   `new URL("http://[::ffff:127.0.0.1]/").hostname === "[::ffff:7f00:1]"`
2. `url-guard.ts:90` 去掉方括号 → `::ffff:7f00:1`
3. `url-guard.ts:93` 的显式 metadata 黑名单只比对字面量 `"169.254.169.254"` 和
   `"fd00:ec2::254"` → `::ffff:a9fe:a9fe` **不匹配，黑名单被绕过**
4. `net.isIP("::ffff:7f00:1") === 6` → 进入 `isPrivateV6`
5. `isPrivateV6` 的前缀检查（`fe8/fe9/fea/feb`、`fc/fd`、`ff`）对以 `::` 开头的地址全不命中
6. `url-guard.ts:197` 的 v4-mapped 分支正则 `/:ffff:([0-9.]+)$/` **只认点分十进制**。
   结合第 1 步 → **该分支是死代码，真实 URL 永远到不了**
7. `return false` → 判为公网 → 放行

## 要做的事

修 `packages/core/src/url-guard.ts`，使 v4-mapped IPv6 地址被正确识别为其映射的 IPv4 地址：

1. `isPrivateV6` 里把 `::ffff:` 前缀的地址解析出末 32 位，还原成点分 IPv4，
   复用已有的 `isPrivateV4` 判定。**必须同时支持两种书写形式**：
   十六进制组（`::ffff:7f00:1`，真实 URL 的形态）与点分（`::ffff:127.0.0.1`，
   手写/日志里可能出现的形态）。
   推荐做法：把 v6 地址展开为 16 字节后判断是否匹配 `::ffff/96` 前缀，再取末 4 字节判 v4。
   这比正则更不容易漏掉压缩写法（如 `::ffff:0:7f00:1`、大小写混写）。
2. **第 3 步的显式 metadata 黑名单也必须同步覆盖 v6 映射形式**——修好第 1 点后
   `::ffff:a9fe:a9fe` 会被 `isPrivateV6` 判为私网，但那道黑名单是"即使 allowlist 也不放行"
   的独立保险，其语义不能只靠私网判定兜底。请让它同样识别 v4-mapped 形式。
