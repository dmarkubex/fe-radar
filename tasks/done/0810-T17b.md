## 本任务要做的事

### 1. `runBriefingPush` 改成 CAS claim-first（镜像 `daily-push.ts` 的

`insertClaim`/`authorizeWebhookAttempt`/`reclaimFailedOrStale`/
`markStalePendingFailed`/`finalizePush`/`sendWithCas` 这一组函数）

业务键 `(briefingId, targetId)`，对应 `briefingPushes` 表（已有 `UNIQUE(briefing_id, target_id)`

- `pushStatus` CHECK 三态 + `attemptCount` + `pushedAt`，规格已确认不需要新迁移）。
  当前 `runBriefingPush`（:142-277）是 check-then-send（先 SELECT 判断
  `existing.pushStatus==='succeeded'`，没有就发，发完 `onConflictDoUpdate` upsert）——
  这是本次要修的核心并发缺陷（两个不同 job 可能被 3 副本 worker 中的不同副本
  并发处理，参见规格开头"已核实事实"第 1 条）。

改造后：INSERT claim（`ON CONFLICT DO NOTHING RETURNING`，target 为
`[briefingPushes.briefingId, briefingPushes.targetId]`）→ 拿到 claim 才能进
授权+发送循环；没拿到 claim 走 SELECT 现状分支（`succeeded` 跳过计成功、
`failed` 记录不自动重试、`pending` 且 stale 则标记失败并告警一次、非 stale
`pending` 静默跳过）。

区分 scheduled 与 manual 两条路径（对应 `daily-push.ts` 的
`processTargetScheduled`/`processTargetManual`）：

- scheduled（`runScheduledBriefingPush` 内部调用）：`failed`/非-stale `pending`
  一律不发送，不 reclaim。
- manual（API 路由触发的 `runBriefingPush` 直接调用）：`failed` 或 stale
  `pending` 走 `reclaimFailedOrStale`（合并 reclaim + 首次授权成一条 UPDATE，
  镜像 `daily-push.ts` 的写法）。

`runBriefingPush` 目前是单一入口（`bootstrap.ts` 手工重推分支和
`runScheduledBriefingPush` 都调它），需要拆出一个内部参数区分 scheduled/manual
（比如加一个 `mode: "scheduled" | "manual"` 参数，`runScheduledBriefingPush`
传 `"scheduled"`，`bootstrap.ts` 里手工重推分支传 `"manual"`，API 路由那边
不直接调这个函数，走队列——不用改路由的调用方式，只需要 `bootstrap.ts`
在 dispatch 手工 job 时告诉 `runBriefingPush` 这是 manual）。

### 3. `runScheduledBriefingPush` 接收 `now`，`scheduleLatestBriefingPush` 接收

`reportDate` 参数（规格第 5 节单一时钟）

- `runScheduledBriefingPush(options: { now?: Date })`——目前已经接受
  `options.now`（:294-297）用于时间门判断，但 :328
  `scheduleLatestBriefingPush()` 调用时没有把这个 `now` 传下去，内部
  `scheduleLatestBriefingPush`（:341-368）自己又调了一次
  `nowInAppTimezone()` 取"今天"——这是规格明确要修的双时钟 bug。
  改成 `scheduleLatestBriefingPush(reportDate: string)`，`reportDate` 由
  `runScheduledBriefingPush` 内已经算出的 `now`（`dayjs(...).tz(APP_TIMEZONE)`）
  派生后传入，函数内部不再调用任何墙钟。
- `runBriefingPush` 内部当前 `const now = new Date();`（:147）用于
  `isBusinessDay(now, holidaySet)` 工作日判断——**scheduled 路径**必须改用
  调度层传下来的日期（与上面 `reportDate` 同一个值，不要在 `runBriefingPush`
  内部重新取墙钟）；**manual 路径**（API 触发的历史简报重推）保持现状用
  `new Date()`（这是已知的、本轮不要求修的技术债——重推历史简报被"今天"
  工作日门拦截，参见 `.ai/reviews/2026-08-10-dp-r1-qoder.md` 的 F8，Low 级，
  不在本任务范围，不要顺手改，除非改动成本为零且不影响其它逻辑）。
- `bootstrap.ts` 的分钟 tick 分支（T17a 已经采样过 `const now = new Date();`）：
  把 `runScheduledBriefingPush()` 改成 `runScheduledBriefingPush({ now })`，
  使用**同一个** `now` 变量，不要重新 `new Date()`。
