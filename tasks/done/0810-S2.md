## 背景

`apps/web` 的本地登录有一层失败限速（每 username / 每 IP 各 5 次，锁 15 分钟），
实现分布在 `packages/core/src/quota.ts` 与 `apps/web/lib/auth/login-rate-limit.ts`。
**该限速在并发下不生效**，且 IP 维度可被伪造头绕过。

## 已观测缺陷（必须回代验算）

### 缺陷 A — check-then-act 竞态（High）

已读码确认，非推测：

- `packages/core/src/quota.ts:114-122` 的 `LOGIN_ADMIT_LUA` 是**纯读**脚本：
  两次 `redis.call('GET', ...)` + 比较 + 返回 0/1。**没有 INCR，没有任何预占。**
- 计数写入在 `recordLoginFailureBoth`，由 `apps/web/auth.ts` 的 `authorize()`
  **在 bcrypt 校验失败之后**才调用。
- bcrypt work_factor=12，单次约 250ms。

**失败场景**：并发提交 100 个错误密码。全部请求在计数仍为 0 时通过 `admitLoginAttempt`，
全部进入 bcrypt，全部完成猜测。限速上限 5 形同虚设，单波即可远超。

### 缺陷 B — XFF 无条件可信 + `unknown` 共享键（Medium）

`apps/web/lib/auth/login-rate-limit.ts:59-67` 从 `X-Forwarded-For` 取客户端 IP。
`deploy/stack.yml:37` 直接发布 Swarm ingress，**没有会重写该头的可信代理层**。

**失败场景 B1**：攻击者每次请求轮换伪造 `X-Forwarded-For`，IP 维度限速完全绕过
（username 维度仍能挡单账户爆破，但跨账户喷洒不受约束）。
**失败场景 B2**：取不到 XFF 时所有请求共用字面量 `"unknown"` 作为 IP 键 →
攻击者故意不带 XFF 连续失败 5 次，即可把**所有**无 XFF 的正常用户一起锁死 15 分钟（拒绝服务）。

## 要做的事

### A — 改为 bcrypt 前原子预占

1. 新增（或改造）一个 Lua 脚本，在**一次原子执行**内完成：读两键 → 任一超限则返回拒绝 →
   否则两键各 `INCR` 并在首次设置 TTL → 返回放行。即"先占坑再验证"。
2. `authorize()` 在**调用 bcrypt 之前**执行该预占。超限直接拒绝。
3. **登录成功时回滚本次预占**（两键各 `DECR`，不要 `DEL`——`DEL` 会把同一 IP 下
   其他用户的失败计数一并清掉）。登录失败时保留预占，不要再额外 INCR
   （否则一次失败计两次）。
4. Redis 不可达时维持现有 **fail-open** 行为（避免 Redis 故障锁死全员登录）。
   这是既有的有意设计，不要改成 fail-closed。

### B — XFF 可信边界

1. 只有在**确实存在会重写 XFF 的可信代理**时才启用 IP 维度。用一个显式环境变量控制
   （例如 `TRUST_PROXY_HEADERS`），**默认关闭**。
2. 关闭时：使用可信 peer 地址；取不到就**跳过 IP 维度**（username 维度仍生效），
   **不要**回退到共享的 `"unknown"` 键。
3. 在 `deploy/stack.yml` 与 `deploy/compose.portainer-current.yml` 的注释里写明该变量的
   语义与当前部署应取的值。

   取不到 peer 地址时不产生共享 `"unknown"` 键。
