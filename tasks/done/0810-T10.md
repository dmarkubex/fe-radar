# 缺陷 B-1（High）— RE2 逐 item 重新编译，内存不回收

## 已观测事实（主会话已实测）

`apps/worker/src/fetchers/quotes/rsshub-extract.ts:214` 循环遍历 feed 的每个 item，
对每个 item 都调 `applyRegexRules(plainText, regexRules)`；其内部 `:95`
`for (const rule of rules)` 里对每条规则都 `new RE2(rule.pattern, "i")`。
**每次调用都新建 RE2 实例，不复用。**

主会话实测（`apps/worker` 目录，`node --expose-gc`）：

```
5000 item × 20 rule = 100,000 次 RE2 构造
耗时: 870ms
RSS: 56.9MB → 循环后 131.3MB → 显式 gc() 后 131.4MB（不回落）
```

**失败场景**：不匹配任何规则的 feed（有早退机制，但一旦没有规则命中就会跑满全部
item×rule 组合，这正是恶意/畸形 feed 最容易触发的情况）会造成显著 CPU 时间和
无法被 JS GC 回收的原生内存增长，长期运行可能导致 worker 被 OOM kill。

## 要做的事

把规则编译提到 item 循环之外，每次 `fetchQuotes` / 每次抓取只编译一次：

1. 在遍历 feed items **之前**，把 `regexRules` 逐条编译成 `{ metricKey, re: RE2, group, multiplier }`
   的列表；**构造失败（不支持的语法）在这一步就 warn 并跳过该规则，只 warn 一次**，
   不要放进 item 循环里重复 warn。
2. `applyRegexRules`（或改名后的等价函数）改为接受**已编译**的规则列表，
   item 循环内只做 `re.exec(text)`，不再 `new RE2(...)`。
3. 保持原有语义不变：找到第一个匹配即返回；无规则匹配、无规则配置的行为都不变。

## 允许修改的文件（清单外即越界）

```

```

## 必须新增的测试

1. **无效规则只 warn 一次**：一批 100 个 item 的 feed 配一条不支持语法的规则
   （如含前瞻 `(?=x)`），断言 warn 日志只出现 1 次而不是 100 次。
2. **性能回归**：5000 item × 20 rule 的不匹配场景，断言耗时在合理上限内
   （给一个宽松阈值，如 <200ms，本机实测编译一次后应远快于逐 item 编译的 870ms）。
3. 回归：既有真实业务规则、真实 seed 正则用例继续通过（不要破坏 T4/S8 已有的行为）。

# 缺陷 B-2（High）— Web 镜像可能意外安装 worker 的 re2，无编译工具链兜底

## 已观测事实（主会话已实测）

`deploy/Dockerfile.web:27` `COPY apps/worker/package.json apps/worker/package.json`，
`:34` `RUN pnpm install --frozen-lockfile --child-concurrency=1`——**无 `--filter`，
整个 workspace 一起装**，会连带触发 worker 的 `re2` 依赖安装脚本
（预编译下载失败则 fallback `node-gyp rebuild`）。

而 `Dockerfile.web` 的 deps 阶段（第 1-34 行）**零处 `apt-get install python3 make g++`**。
web 运行时不需要 `re2`（RE2 只在 worker 的 `rsshub-extract.ts` 用到）。

**失败场景**：某次构建时 GitHub releases 对 RE2 预编译产物限流/不可达
（worker 侧实测过这一步耗时 21 秒，非零概率失败），
web 镜像的 deps 阶段会尝试 fallback 编译，但没有工具链 → 直接构建失败。
**本轮从未验证过 web 镜像的真实 Docker 构建**，只验证过 worker。

## 要做的事

让 web 镜像的 `pnpm install` 只安装 web 实际需要的依赖图，不拉进 worker 专属的 `re2`。

**推荐做法**：`pnpm install --frozen-lockfile --filter=@fe-radar/web...`
（`...` 包含其依赖的 workspace 包，如 `packages/core`、`packages/db` 等，
不含 `apps/worker`）。

**必须验证**：改完后确认 `apps/web` 实际用到的所有 workspace 依赖仍被正确安装
（读 `apps/web/package.json` 的 `dependencies`，逐个确认 `--filter` 表达式能覆盖到）。
若 `--filter` 语法在这个 pnpm 版本下有兼容性问题，改用其它等效收窄方式，
并在 handoff.md 说明选择的具体命令和验证依据。

**是否需要保留 `COPY apps/worker/package.json`**：若收窄 `--filter` 后不再需要这份
manifest 参与 install，一并去掉该 COPY 行（减少不必要的层）；若 `--filter` 解析
workspace 依赖图仍需要读到所有 package.json（pnpm workspace 的常见要求），则保留 COPY
但确认它不再触发该 package 的实际依赖安装。**不确定就保守保留 COPY，只改 install 命令**。
