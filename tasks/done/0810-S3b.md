## 背景

`users.token_version` 是本批次新增的撤权机制（migration `0057_users_token_version.sql`）：
改角色 / 停用 / 合并确认 / 凭据轮换时递增该列，`requireFreshRole()` 比对 JWT 内的
`tokenVersion` claim 与库里的当前值，不一致即判 stale、强制重新登录。

**钉钉内免登这条登录路径不写这个 claim，而校验侧又对"缺 claim"显式放行，
两处叠加使该账号的撤权机制永久失效。**

## 已观测缺陷（必须回代验算）

- `apps/web/lib/auth/dingtalk-inapp-provider.ts:19` / `:196` —— 内免登返回的用户对象
  **不含 `tokenVersion`**（对比本地凭据登录路径 `apps/web/auth.ts`，它是写的）。
- `apps/web/lib/auth/token-freshness.ts:63` 附近 —— 对**缺少 `tokenVersion` claim**
  的 token **仅比较角色后放行**，不判 stale。

**失败场景**：admin 用户经钉钉内免登获得一个无 `tokenVersion` 的 JWT。
此后该账号即使被停用、降权或轮换凭据（`token_version` 递增），
该 JWT 仍能通过 `requireFreshRole` 的版本校验（因为"无 claim → 放行"），
可继续访问全部特权 API。**这不是有界窗口，是永久绕过**——
只要不改角色，token 在其自然有效期内始终有效，且每次内免登都会再签发一个同样无版本的新 token。

同一放行分支还覆盖**升级前签发的旧 token**（升级瞬间所有存量 token 都无该 claim）。

## 要做的事

1. `dingtalk-inapp-provider.ts` 在返回用户对象时带上 `tokenVersion`
   （值取自 `mergeOrCreateUser` 的返回，与本地登录路径保持一致）。
   **先 `grep -rn` 确认还有没有第三条登录路径**（例如钉钉扫码登录 provider）
   也漏了这个字段——本项目有"改一处漏一处镜像实现"的前科。
2. `token-freshness.ts` 把"缺 `tokenVersion` claim"从**放行**改为**判 stale**。

3. **【S3a 验收时新发现，必须一并修】`requireFreshViewer()` 里有一处更早的放行分支，
   会让第 2 点的修复完全绕过。** 当前实现（S3a 引入）：

   ```ts
   // 生产 JWT 在登录时写入 tokenVersion；缺省时跳过查库（遗留窗口 / 测试 mock）。
   if (typeof user.tokenVersion !== "number") {
     return null; // ← 直接返回，根本不调用 verifyTokenFreshness
   }
   ```

   它在 `verifyTokenFreshness` **之前**返回，所以只改 `verifyTokenFreshness` 内部
   对缺省版本的判定是**没有用的**——控制流到不了那里。必须删掉这个早返回，
   改为把 `tokenVersion: undefined` 传下去，由 `verifyTokenFreshness` 统一裁决。

   **参照 `gateAdminPage()` 的写法**——它已经是对的：

   ```ts
   tokenVersion: typeof token.tokenVersion === "number"
     ? token.tokenVersion
     : undefined;
   ```

   两个闸门必须语义一致。当前 `requireFreshViewer` 跳过查库、`gateAdminPage` 不跳过，
   这个不一致本身就是缺陷。

   **影响面（说明为什么这条是 High 而不是清理性改动）**：内免登不写 `tokenVersion`
   （已实测：`grep -n tokenVersion apps/web/lib/auth/dingtalk-inapp-provider.ts` 零命中），
   所以**所有经钉钉内免登的会话都命中这个早返回**，S3a 新加的 11 个只读接口闸门
   对它们全部跳过查库。内免登是本项目主力登录路径，等于头号受众未被保护。

   注意 `requireFreshViewer` 里还有一处"无会话（id 与 role 均 undefined）→ return null"
   的分支。**那一条经核实是安全的**（middleware matcher 已覆盖全部相关 route，
   生产上无会话请求到不了 handler），**不要动它**，动了会破坏现有单测。

### 关于第 2 点的迁移窗口（必须处理，不要直接一刀切）

改成 fail-closed 会让**所有升级前签发的存量 token 立即失效**，全体在线用户被登出一次。
这是可接受的一次性成本，但**必须**：

- 在 `handoff.md` 与 `deploy/` 相关注释里写明"本次发布会强制全员重新登录一次"。
- 确认登出后的跳转体验正常（不是白屏或无限重定向）。

如果你判断需要一个过渡期开关，可以加，但**默认必须是 fail-closed**，
且开关要有明确的移除计划写进 handoff.md。不要默认 fail-open。
