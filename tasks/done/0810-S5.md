# 缺陷 A — 生产 compose 漏配 `FETCH_INTERNAL_ALLOWLIST`，守卫上线即打死 RSSHub（High）

## 已观测事实

- `deploy/stack.yml:113` 给 worker 配了 `FETCH_INTERNAL_ALLOWLIST: rsshub`。
- **当前生产实际使用的 `deploy/compose.portainer-current.yml` 没有这一项**，
  只有 `RSSHUB_BASE_URL: http://rsshub:1200`。
- `SSRF_GUARD_ENABLED` 默认开启。
- `url-guard.ts` 的端口检查先于 allowlist 之外的判定，`1200` 不在 `ALLOWED_PORTS`。

**失败场景**：按 current compose 部署新 worker →
`assertPublicFetchUrl("http://rsshub:1200/...")` 返回 `PORT_BLOCKED:1200` →
quotes-fetch 与所有经 RSSHub 的 RSS 源全部 `FETCH_SSRF_BLOCKED` →
v1.1 铜锂行情简报断供。`stack.yml` 自己的注释就预警过这个后果。

## 要做的事

`deploy/compose.portainer-current.yml` 的 worker（以及 scheduler，如果它也抓取）
env 补 `FETCH_INTERNAL_ALLOWLIST: rsshub`，与 `stack.yml` 对齐。

# 缺陷 B — HTTPS 启动断言与 compose 注释自相矛盾，按文档部署即 crash-loop（High）

## 已观测事实

- `apps/web/instrumentation.ts:11-17` 在生产启动时，若 `AUTH_URL` / `NEXTAUTH_URL`
  是 `http://` 就直接 `throw`。
- `deploy/compose.portainer-current.yml:155-157` 附近的注释明确写着
  "内网过渡期可 `http://10.1.20.156:3013`"。
- 项目是**内网 only** 部署，当前生产 origin 就是 `http://10.1.20.156:3013`
  （见 `handoff.md`、`daily_push_config.base_url`）。

**失败场景**：运维按 compose 注释填 `NEXTAUTH_URL=http://10.1.20.156:3013` →
更新 stack → web 容器启动即抛错退出 → 反复重启 → **全站不可用**。
这是"文档引路、代码埋雷"。

## 要做的事（二选一，选完在 handoff.md 说明理由）

- **(a) 推荐**：断言放宽为"非空即可"；`http://` 时打 **WARN 级结构化日志**
  并强制 `useSecureCookie=false`（http 下 Secure cookie 发不出去，必须一致）。
  把 HTTPS 硬性要求推迟到真正切外网时再由 `docs/runbook/external-https-deployment.md` 约束。
- (b) 保留 `throw`，但**同时**删掉 compose 里"内网过渡期可 http"的承诺，
  并给出内网 TLS 的落地步骤。

**不要两边都不动**。当前状态是确定性的部署陷阱。

# 缺陷 C — Playwright 两条出网路径绕过守卫（High）

## 已观测事实

### C1 — robots.txt 预取用裸 fetch

`apps/worker/src/fetchers/playwright.ts:92` 附近调 robots 检查，
`apps/worker/src/lib/robots.ts:47` 用的是**全局 `fetch`**：无 SSRF 守卫、
自动跟随重定向、`response.text()` 无字节上限。

**失败场景**：合法公网源的 `/robots.txt` 返回 `302 → http://127.0.0.1/`
或 metadata 地址 → 在浏览器 route guard 装上之前就完成了 SSRF。

### C2 — Chromium 主框架重定向链无守卫

`apps/worker/src/fetchers/playwright.ts:92-97` 的前置 guard 只验 `listUrl` 本身。
Chromium 网络栈**内部消化 30x 跳**，`page.route` 对重定向产生的新请求**不触发**
（playwright#3993 官方确认 "not allow intercepting them"）。
`goto` 之后也没有校验最终落点——`PageLike` 接口（`:36-42`）连 `url()` 都没有。

**失败场景**：通过 guard 的公开 listUrl `302 → http://169.254.169.254/` →
Chromium 直接导航到内网页面，`$$eval` 把其内容抽取进时间线。

## 要做的事

1. **C1**：让 `robots.ts` 的抓取走带守卫的 fetch 边界——
   请求前 `assertPublicFetchUrl(url)`、`redirect: "manual"` 逐跳复验、加响应字节上限。
   注意 `robots.ts` 同时被 http/playwright/firecrawl 多处调用，改一处即全线受益，
   但**必须确认不会把合法公网抓取误拦**。
2. **C2**：`PageLike` 接口加 `url(): string`；`goto` 返回后对 `page.url()`
   重跑 `assertPublicFetchUrl`，不符即抛 `SourceFetchError`。
   并在代码注释里写明**残余风险**：Chromium 自建连、自解析 DNS，
   应用层无法钉住 lookup，DNS rebinding 仍不可闭环，真正的闭环需要出口 ACL 或受控代理。
   **把这条残余风险同时写进 handoff.md**，不要假装已经解决。
