# 缺陷 A — migration 0059 漏掉已绑钉钉的遗留 viewer 行（High）

## 已观测事实

`packages/db/migrations/0059_disable_legacy_viewer_credential.sql:18-20` 的实际条件：

```sql
WHERE username = 'viewer'
  AND role = 'viewer'
  AND dingtalk_id IS NULL;
```

`AND dingtalk_id IS NULL` 使**已绑定钉钉的 viewer 行被整行跳过**。
而账号绑定钉钉时（`apps/web/lib/auth/merge.ts`）**不会清除 `password_hash`**。

**失败场景**：仓库里公开的默认凭据 `viewer` / `viewer-password` 曾创建过一行；
该行后来被自动或人工绑定了钉钉 → 0059 跳过它 → `password_hash` 原样保留。
一旦运维为应急打开 `EMERGENCY_LOCAL_LOGIN=true`，**仓库已知的默认口令仍可直接登录**。

## 要做的事

**新建 migration `0061_*.sql`**（**严禁修改已发布的 0059**，项目硬约束：
已发布 migration 不得原地改，必须走新文件）：

- 覆盖**所有**仍持有该遗留本地凭据的 `username='viewer'` 行，不再按 `dingtalk_id` 分流。
- 已绑钉钉的行：**清除 `password_hash`**（置 NULL）并**递增 `token_version`**，
  但**不要**禁用该账号——它已是正常的钉钉账号，禁用会误伤真实用户。
- 未绑钉钉的行：维持 0059 的语义（禁用 + 递增版本），0059 已处理过的行需幂等（重跑无副作用）。
- 文件头按本项目惯例写：任务号、背景、幂等性说明、`ROLLBACK (manual only)` 段。

## 机械检查 A（必须执行）

1. **守卫列的写入方**（本项目有前科：用 `admin_touched_at` 做守卫，却没人写它，
   导致安全迁移跳过了唯一在漏的行）：
   ```bash
   grep -rn "password_hash" --include=*.ts --include=*.sql packages apps | grep -v node_modules
   grep -rn "token_version\|tokenVersion" --include=*.sql packages/db/migrations
   ```
   确认 `password_hash` 置 NULL 后，本地登录路径会**正确拒绝**（而不是把 NULL 当空口令通过）。
   **这一条必须读 `apps/web/auth.ts` 的 authorize 实测确认**，不能假设。
2. 确认迁移在 `password_hash` 已为 NULL 的行上重跑无副作用（幂等）。

# 缺陷 B — project_codes 无写入方，且从未初始化时 fail-open（High）

## 已观测事实

- `packages/db/migrations/0058_project_codes.sql` 建了空表，注释自述"admin 后台补"。
- 全仓 grep `INSERT INTO project_codes` / `insert(projectCodes)` **零命中**：
  没有 seed、没有 admin API route、没有 admin UI 页面。**唯一填充方式是手工 SQL。**
- `apps/worker/src/handlers/context.ts:176-199` 的 `loadProjectCodes()`
  在 catch 里 `return projectCodesCache?.codes ?? []`。

**失败场景**：新部署尚未人工写入字典 → `loadProjectCodes()` 恒返回 `[]` →
真实项目代号**原样发送给公网 LLM**（DeepSeek / Kimi）。
本批次名义上的核心脱敏修复长期无效，而它承诺的"后台维护入口"并不存在。

## 要做的事（两件，都要做）

### B1 — 补 admin 维护入口

按本项目既有的 `sources` / `entities` admin route 模式，新建 `project_codes` 的
admin-only CRUD route，**必须用 `requireFreshRole(request, "admin")` 守卫**。
UI 页面本任务**不做**（范围外），只要 API 可用 + runbook 写明维护方式即可。

### B2 — 区分「从未初始化」与「一次抖动」，前者 fail-closed

**注意：现有的 fail-open 是有意设计**，`context.ts:191-196` 的注释明确写了理由——
防止一次 DB 抖动把字典清空、代号原样外发。**不要把它整个改成 fail-closed**，
那会让 DB 抖动直接阻塞整条 pipeline。

要区分三种状态：

| 状态                                         | 期望行为                                                 |
| -------------------------------------------- | -------------------------------------------------------- |
| 从未成功加载过（无快照）                     | **阻断公网 LLM 调用**（抛错 / 跳过该 job），不得静默放行 |
| 加载过、这次 DB 抖动                         | 沿用上次成功快照（现有行为，保留）                       |
| 加载成功、字典确实为空（admin 就是没配代号） | **放行**——这是合法状态，不是未初始化                     |

第 1 与第 3 种必须能被区分开。仅凭"数组为空"无法区分，
需要一个显式的"已成功加载过"标记（例如快照对象存在但 codes 为空 vs 快照为 null）。

同时确认 `apps/worker/src/jobs/daily-gen.ts` / `briefing-gen.ts` 等公网 LLM 调用点
在阻断时的行为合理（结构化日志 + 任务失败，而不是静默产出未脱敏内容）。

## 机械检查 B（必须执行）

1. **确认脱敏方向没搞反**：代号字典的用途是把**真实名替换为代号后再出网**，
   不是把代号还原成真名。读 `packages/core/src/scrubber.ts` 确认，结果写进 handoff.md。
2. **确认字典本身不会进入 LLM 请求体**（否则等于把映射表交出去）。
3. **回代验算（强制）**：构造"表不存在 / 查询抛错且无快照"的场景，
   代入修复后逻辑，确认公网 LLM 调用被阻断；再构造"加载成功但表为空"，确认放行。
   两个实际输出都抄进 handoff.md。
